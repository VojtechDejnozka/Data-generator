# Story2Data – implementation plan

## 1. Goal
A prototype web app that turns a **company description + story + complexity parameters** into a
**linked multi-table dataset** in which the story is traceable through causal and temporal
relationships between records. It also provides **evidence** (SQL, charts, step-by-step report),
**what-if** regeneration and a run comparison.

## 2. Architecture overview

### Hybrid generation (key decision)
* `simulation` – deterministic seeded simulator (numpy/pandas). The story is injected through
  **mechanisms** (delivery delay → lower stock → stockout → unfulfilled purchase intents →
  complaints), never by writing the final KPI directly. A small library of effect primitives
  (`trend`, `step`, `ramp`, `seasonality`, `noise`, `event window`) plus a `ScenarioModule`
  interface lets new archetypes be added. Implemented module: `retail_supplier_delay`.
* `llm_dimension` – master data (names, cities, product names, descriptions) is generated by the
  CHEAP model; structural/numeric attributes (IDs, FK assignment, prices within ranges) are set
  deterministically by the module from the seed.
* `llm_rows` – generic path for any story/table: CHEAP generates rows in batches with context
  (valid FK values, period, rules, story timeline), output constrained by a JSON schema derived
  from the column definitions, rows validated (types, FK, PK uniqueness); invalid batches are
  retried with the error message.
* Free text (complaint texts) – CHEAP produces a **template pool per complaint category**
  with placeholders (`{product}`, `{store}`, `{days}` …); the simulator fills them with the actual
  facts from the data (which product was missing, where, how long), so text matches the data.

### Ground truth manifest
Each run stores `manifest.json` (hidden in the UI until requested): affected supplier/products,
delay start, ramp, per-month injected delay, realized lost units/revenue, causal chain with the
realized effect sizes, distractor events with dates.

### Noise, distractors, control group
* Seasonality (weekday + yearly pattern per category, Christmas peak → January dip).
* Random distractors: a store closed for renovation (footfall 0 for ~10 days), a competitor opening
  near one store (genuine local demand drop, affects all suppliers), a one-off short delivery
  disruption at another supplier (a strike week – recovers quickly), price increase in one category.
* Control group = products of non-affected suppliers (same stores, same period). The report shows
  affected vs. control indexed to the pre-story period.

### Determinism
Independent RNG streams per component (`np.random.default_rng([seed, stream_id])`). Demand
(visits and purchase intents) is sampled **independently from stock**, so a what-if with
different knobs shares exactly the same demand. The only differences come from the mechanism.
LLM outputs are cached by input hash and logged per run (`llm_calls.jsonl`), so a run replays
without new calls.

## 4. Data contracts (summary – see `backend/app/contracts`)
* `ScenarioInput` – company, environment, story, complexity params (counts, period, volume,
  story_intensity, seed), optional custom data model text.
* `ScenarioSpec` – `meta` (name, domain, data_language, period_start/end, seed, archetype),
  `tables[]` (name, description, row_count, strategy, columns[name, type, description, pk, fk,
  nullable, enum_values, min, max]), `story` (logline, causal_chain[step: id, mechanism, affected
  entities, start, ramp_profile, expected_impact, tables], ground_truth_facts[], distractors[]),
  `knobs[]` (name, type, default, min/max/options, description, applies_to), `invariants[]`
  (kind: fk | unique | not_null | range | compare | row_count | sql_zero_rows), `evidence[]`
  (id, title, sql, expected, chart, step_id), `dashboard` (widgets[sql, chart, title, x, y, series]).
* `PlannerResponse` – spec + clarifying questions + suggestions (with optional structured patch).
* `GenerationPlan` – work packages (table(s), strategy, depends_on, batches, instructions).
* `ValidationVerdict` – verdict pass/warn/fail, story detectability per causal step, issues
  (severity, table, description, fix, repair action).
* All LLM calls: Gemini `response_mime_type=application/json` + `response_json_schema` (derived from
  Pydantic, `$defs` inlined), Pydantic validation, retry with error message (max 2).

## 6. Phases
F1 LLM client + contracts · F2 planner + input/review UI · F3 generator · F4 checks + validation +
repair · F5 report, data browser, dashboard · F6 what-if + compare · F7 detective · F8 polish,
README, demo script. Each phase ends with tests and a commit. Priority: end-to-end demo first.

## 7. Assumptions
1. **Models** (verified against `models.list()` with the project key and aistudio.google.com docs,
   2026-11-27): STRONG = `gemini-4-carbon`, CHEAP = `gemini-3.5-flash-lite`. The provided key is on
   the **free tier, where Gemini 4 models have quota 0** and Flash models were often 503 (overloaded).
   Therefore the client supports **fallback chains** (`STRONG_FALLBACK_MODELS`, default
   `gemini-3.8-flash,gemini-3.5-flash,gemini-3.5-flash-lite`). A 429 with `limit: 0` skips straight to
   the next model; 429/503 otherwise back off exponentially.
2. SDK: official `google-genai` (v3.6) `client.aio.models.generate_content` with
   `GenerateContentConfig(response_mime_type, response_json_schema, thinking_config)`. If a schema
   is rejected (400, too complex), fall back to JSON mode without schema + Pydantic validation.
3. Storage: SQLite (stdlib, single-file export, read-only URI mode + authorizer for AI SQL).
   DuckDB would be faster for analytics but adds nothing important at this data size.
4. Python 3.13 (3.11+ required; 3.13 is installed locally), managed with `uv`.
5. Default demo size: 10 stores, 240 products, 7 suppliers, 1 500 customers, 15 months,
   ~45 visitors/store/day → roughly 150k transactions. "Objem dat" scales visitors.
6. Jobs are in-process (no Redis/Celery); restarting the server loses running jobs, but finished
   runs are on disk.
7. The UI is in Czech; the code, comments and LLM prompts are in English, and the data language is
   set by the spec (default Czech).
